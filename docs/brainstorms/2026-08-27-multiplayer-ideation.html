Ideation brief · Marked Up × ldpub

Marked Up, multiplayer

2026-08-27 · for John · decision requested: pick the build

An engineer finishes a 486 KB board audit and the only way to review it together is to slack the raw file, download it, and annotate alone. The document is shared; the conversation is not. This brief lays out the ways to make Marked Up a shared canvas, and argues that the two systems you already own are one annotation API away from multiplayer.

The annotation layer itself is not the problem. The problem is that annotations never leave the reviewer's browser: they live in localStorage keyed to a local file path, so there is no URL two people can stand on at once, no attribution, and no thread.

02 · What already exists

Two systems, one seam

Marked Up ~/code/markup

  • Overlay with three modes (text span, pin, rect + screenshot), served by a local Node process; source HTML never modified.
  • All persistence flows through persist.js, a nine-function localStorage adapter. Swap that one module and every mode syncs remotely without knowing it.
  • Already handles source-change detection (content hash → stale annotations flagged for triage) and exports a feedback bundle agents can act on.

ldpub ~/code/ldpub

  • Cloudflare Worker + R2 publishing, gated to @launchdarkly.com by Zero Trust Access. Per-user namespaces: /{user}/{project}/.
  • The Worker independently verifies the Access JWT and gets back the caller's email. Every request arrives authenticated.
  • Publish CLI with service tokens, stable URLs on republish, R2 metadata layer already in place.

Hosting, auth, identity, and the annotation UI are all built. The missing piece is a place annotations live that both browsers can read and write. That is one JSON file in R2 and two Worker routes.

04 · The build

Teach ldpub to hold the conversation

The Worker wraps published HTML with the Marked Up overlay at serve time, exactly as the local server does today (the wrapper is already idempotent). The client swaps its localStorage adapter for a remote driver speaking to two new routes. Authorship is stamped server-side from the verified JWT, so nobody logs into anything; being on the page is being signed in.

Two endpoints carry all of it. GET asks the Worker for every note on the doc; PUT hands it one note to keep. Here is the full exchange when you review his audit:

markup pull <url> is step 3 run from a terminal: same GET, written to disk as the standard feedback bundle for his agent.

Annotation record, extended

{ id, mode, cssPath, note, pinNum,   // existing
  author:    "eng@launchdarkly.com", // stamped by Worker
  createdAt, updatedAt,
  state:     "open | resolved | pending",
  replies:   [{ author, text, at }] // phase 2
}

Merge is last-write-wins per annotation id; ids are already collision-safe. Rect screenshots move to R2 objects instead of inline data URIs.

Today's work, four units

  • Unit A · Worker: GET/PUT …/annotations + GET /api/me, JSON in R2, serve-time overlay injection. The middle lane, steps 1 through 4.
  • Unit B · Client: remote persist driver with the same nine-function surface, ETag polling, author chips on pins and popovers. The browser lanes, steps 3 through 5.
  • Unit C · CLI: markup publish <file> gets the doc into R2 before step 1; markup pull <url> replays step 3 from a terminal.
  • Unit D · Ship: publish the CE Jira board audit, drop one URL in Slack, run the whole sequence for real.

Units are independent; they fan out to parallel agents and converge on the publish. Done means the audit is reviewed at one URL by both of you, today.

05 · The ladder

Where this goes after today

Phase 1 · Today

One shared canvas

Publish, annotate, poll, attribution. Export unchanged, so the existing agent loop keeps working while humans get a shared page.

Phase 2 · This week

The conversation

Replies and resolve states on every annotation (the PR-review grammar), Slack ping when notes land, and markup pull so his agent reads feedback straight from the API. The agent becomes a third participant that can answer into a thread: fixed in rev 3.

Phase 3 · Later

The room

A Durable Object per document: live presence and cursors, deep links to a specific pin, a multiplayer dashboard across all open reviews, and version triage in the UI when a doc is republished.

What this doesn't settle
  • ldpub is a provisioned prototype; confirming the Worker is live (and re-running the idempotent provision script if not) is step zero of the build.
  • Two writers saving the same JSON in the same second can drop a write under R2 read-modify-write. Acceptable at two players; the Durable Object in phase 3 removes it.
  • Annotations must survive a republish. The local source-hash triage flow covers this, but it needs to be carried through the sync layer, not assumed.
  • Republish currently has a seconds-long 404 window (delete-then-put).
  • The engineer needs a service token to publish himself; until one is minted, the interim path is he slacks the file and you publish it.
  • Zero Trust free tier caps at 50 seats. Fine for the team, a decision point before org-wide rollout.
